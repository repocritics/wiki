# pulumi/pulumi

> Infrastructure as Code in general-purpose programming languages — the CLI, engine, and language SDKs.

[GitHub repo](https://github.com/pulumi/pulumi) ·
[Official website](https://www.pulumi.com) ·

## Overview

Pulumi is an infrastructure-as-code (IaC) tool that lets you describe cloud resources in real programming languages — TypeScript/JavaScript, Python, Go, C#/F#/VB.NET, Java, and (as a data-only option) YAML — instead of a purpose-built DSL[^1]. You write a normal program; Pulumi evaluates it to produce a desired-state resource graph, diffs that graph against recorded state, and applies the minimal set of create/update/delete operations. The company (Joe Duffy et al.) launched it publicly in 2018 and reached 1.0 in 2019[^2].

The defining bet is that infrastructure benefits from the same abstractions as application code: loops, functions, classes, conditionals, unit tests, and package managers, rather than HCL's copy-paste-plus-modules idiom. That bet is also the central tension. Using a Turing-complete language means your infra description is a *program that runs*, with all the non-determinism, side effects, and dependency-resolution surprises that implies. The `Output<T>` type — Pulumi's model for values that are unknown until a resource is provisioned — is the concrete place most newcomers meet this tension.

Pulumi is frequently compared to Terraform. The engineering substrate overlaps heavily: a large fraction of Pulumi's cloud providers are *bridged* from the corresponding Terraform providers[^3], so provider coverage and behavior often track the Terraform ecosystem. The differences are the language surface, the state/secrets handling, and the licensing — Pulumi has stayed Apache-2.0 throughout, while Terraform moved to the BUSL in 2023.

## Getting Started

```bash
curl -fsSL https://get.pulumi.com | sh
```

```bash
mkdir infra && cd infra
pulumi new aws-typescript      # scaffolds a project + stack
```

```typescript
// index.ts — an S3 bucket and a dependent object
import * as aws from "@pulumi/aws";

const bucket = new aws.s3.BucketV2("data");

new aws.s3.BucketObject("readme", {
    bucket: bucket.id,               // Output<string> — resolved after create
    key: "README.txt",
    content: "managed by pulumi",
});

export const bucketName = bucket.id; // stack output
```

```bash
pulumi up          # preview a diff, then apply
pulumi stack output bucketName
pulumi destroy     # tear it all down
```

## Architecture / How It Works

Pulumi's engine and CLI are written in Go. A `pulumi up` orchestrates several processes over gRPC:

1. **Language host** — a per-language runtime (`pulumi-language-nodejs`, `-python`, `-go`, etc.) executes your program. Constructing a resource object doesn't call the cloud directly; it registers the resource with the engine and returns an object whose properties are `Output<T>` values.
2. **Deployment engine** — builds the resource graph from those registrations, computes dependencies from `Output` data-flow, diffs against the last-known state, and schedules operations in dependency order (parallelized where independent).
3. **Resource providers** — separate plugins (one per cloud/service) that implement CRUD via `Check`/`Diff`/`Create`/`Update`/`Delete`. Many are generated by bridging existing Terraform providers[^3]; others are *native* — e.g. `aws-native` (AWS Cloud Control API) and `azure-native` (generated from Azure's API specs).

**`Output<T>`** is the load-bearing abstraction. Because a resource's real ID/ARN/IP doesn't exist until provisioning, dependent values are wrapped and can't be used as plain strings. You compose them with `.apply()`, `pulumi.interpolate`, or `pulumi.all([...])`. This is what makes the dependency graph automatic — but it's also the single most common source of beginner confusion.

**State** is a JSON document (the "checkpoint") recording every resource's URN, inputs, and outputs. It lives in a *backend*: Pulumi Cloud (the default SaaS, app.pulumi.com) or a self-managed backend — S3, Azure Blob, GCS, or the local filesystem[^4]. Secrets are encrypted per-value inside state using the stack's configured encryption provider (Pulumi Cloud's key service by default, or a KMS/passphrase provider you choose).

**Automation API** exposes the engine as a library, so you can drive `up`/`preview`/`destroy` programmatically from your own code instead of shelling out to the CLI[^5] — the basis for self-service platforms and CI integrations.

## Production Notes

**State backend choice is a fork in the road.** The self-managed backends (S3/Azure/GCS/local) store the checkpoint but do *not* provide the Pulumi Cloud features many teams assume — RBAC, deployment history UI, drift detection, policy enforcement, and audit logs live in the SaaS. Concurrent-update locking exists on cloud backends and on some object-store backends, but the local backend gives you no locking; two simultaneous `pulumi up`s can corrupt state.

**Bridged providers lag upstream.** Because most providers are generated from Terraform providers, a brand-new upstream resource or attribute may not appear in Pulumi until the bridge is regenerated and released. Provider versions are pinned per-project and schema mismatches surface as diff noise or plan errors. Pin deliberately and upgrade providers on their own cadence.

**Your program runs on every operation.** Side effects in the program body (writing files, calling APIs, `Math.random()`, timestamps) execute on every `preview` and `up`, and non-deterministic inputs produce spurious diffs. Keep the program a pure description; push imperative work into resource providers or `Command`/dynamic providers.

**`Output` ergonomics.** Trying to `if`/string-concatenate an `Output<T>` as a plain value is the top beginner mistake. Everything derived from a resource output must stay inside `apply`/`interpolate` until the engine resolves it; leaking an unresolved output into a plain string yields `Calculating...`-style placeholders.

**Importing and adopting existing infra.** `pulumi import` can bring unmanaged resources under management and generate code, but the generated code often needs hand-cleanup, and mismatches between imported state and provider defaults cause immediate replace/update diffs. Budget time for reconciliation.

**Refresh and drift.** `pulumi refresh` reconciles state with reality but can be slow on large stacks and will happily record out-of-band changes as the new baseline. Large stacks (thousands of resources) also slow preview/up because the whole graph is walked each run; splitting into multiple stacks with stack references is the standard scaling move.

## When to Use / When Not

**Use when:**
- Your team already writes TypeScript/Python/Go/C# and wants to reuse those skills, tests, and package managers for infra.
- You need real abstraction (loops, conditionals, shared component libraries) that HCL makes awkward.
- You want to embed provisioning inside an application or platform via the Automation API.
- You want an Apache-2.0 IaC tool and want to avoid Terraform's BUSL licensing question.

**Avoid when:**
- Your organization has standardized on Terraform/OpenTofu and its module ecosystem, tooling, and hiring pool.
- You want infra descriptions that are guaranteed side-effect-free and trivially reviewable — a constrained DSL is easier to reason about than a general-purpose program.
- You're single-cloud and a native tool (CloudFormation, ARM/Bicep, GCP Deployment Manager) covers your needs with vendor support.
- You want to avoid a SaaS dependency for team features and aren't prepared to operate a self-managed backend without them.

## Alternatives

- hashicorp/terraform — the incumbent; HCL DSL, largest provider/module ecosystem, BUSL-licensed since 2023. Use it when ecosystem breadth and team familiarity outweigh wanting a real language.
- opentofu/opentofu — MPL-2.0 community fork of Terraform created after the license change. Use it when you want Terraform compatibility under an OSI license.
- aws/aws-cdk — real languages that synthesize to CloudFormation, AWS-only. Use it when you're all-in on AWS and want first-party support.
- hashicorp/terraform-cdk (cdktf) — real languages that generate Terraform. Use it when you want Pulumi-like ergonomics but must keep Terraform as the execution engine.
- crossplane/crossplane — Kubernetes-native, control-plane / reconciliation model. Use it when you want continuously-reconciled infra managed as k8s CRDs rather than run-to-completion applies.
