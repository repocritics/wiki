# AutoFixture/AutoFixture

> Convention-based test data generation for .NET — fills in the "Arrange" phase of unit tests so you only write the parts that matter.

[GitHub repo](https://github.com/AutoFixture/AutoFixture) ·
[NuGet](https://www.nuget.org/packages/AutoFixture) ·
[License: MIT](https://raw.githubusercontent.com/AutoFixture/AutoFixture/master/LICENCE.txt)

## Overview

AutoFixture generates anonymous test data — integers, strings, and whole object graphs — so unit tests don't have to hand-construct objects whose exact values are irrelevant to what's being tested. It is a generic implementation of the Test Data Builder pattern, created by Mark Seemann (the `ploeh` blog) and originally hosted on CodePlex before moving to GitHub in 2012[^1]. Seemann later stepped back from day-to-day maintenance; the library is now community-maintained under the AutoFixture organization[^2].

The core idea is the `Fixture` class and its `Create<T>()` method: ask for a `T`, and AutoFixture reflects over the type, picks a constructor, and populates it recursively with generated values. Strings come out as property-name-prefixed GUIDs, numbers as small positive integers, collections with a few elements. The payoff is refactoring-safe tests — add a constructor parameter and existing tests keep compiling because AutoFixture supplies the new argument. The cost is that your test data is opaque and semi-random, which is the library's defining tension: it removes boilerplate but makes it easy to write tests that don't actually assert on the data they run against.

AutoFixture is not a mocking library or an assertion library. It sits alongside xUnit/NUnit and Moq/NSubstitute/FakeItEasy through a set of integration packages, and its most declarative form — the `[AutoData]` xUnit attribute that feeds generated arguments straight into a test method's parameters — only works once those integrations are wired in.

## Getting Started

```bash
dotnet add package AutoFixture
# optional integrations:
dotnet add package AutoFixture.AutoMoq      # auto-mock interface deps
dotnet add package AutoFixture.Xunit3       # [AutoData] for xUnit v3
```

```csharp
using AutoFixture;
using Xunit;

public class CalculatorTests
{
    [Fact]
    public void Echo_returns_input()
    {
        var fixture = new Fixture();

        int expected = fixture.Create<int>();     // e.g. 148
        var sut = fixture.Create<Calculator>();   // constructed + populated

        Assert.Equal(expected, sut.Echo(expected));
    }
}
```

```csharp
// Declarative form — arguments generated by AutoFixture via the attribute.
[Theory, AutoData]
public void Echo_returns_input(int expected, Calculator sut)
{
    Assert.Equal(expected, sut.Echo(expected));
}
```

## Architecture / How It Works

The engine is a composition of `ISpecimenBuilder` instances. A `Create<T>()` call issues a *request* (typically a `Type`) into a pipeline; each builder either handles the request and returns a specimen or returns a sentinel `NoSpecimen` to pass it along. The default `Fixture` stacks dozens of builders — one for primitives, one for enums, one for `DateTime`, one that reflects over constructors, one that assigns writable properties post-construction, and so on. This chain-of-responsibility design is what makes AutoFixture extensible: a `Customization` is just a bundle of builders inserted into the pipeline.

Constructor selection matters and trips people up. By default `Fixture` uses `ModestConstructorQuery` — the constructor with the *fewest* parameters. The auto-mocking integrations (e.g. `AutoMoqCustomization`) change relevant behavior so that interface and abstract dependencies resolve to mocks instead of failing. You can force the greediest constructor with `GreedyConstructorQuery` when the modest one leaves an object under-populated.

Recursion is handled by *behaviors*, which wrap the whole pipeline. Given a graph with a circular reference (A holds B, B holds A), the default `ThrowingRecursionBehavior` detects the loop and throws `ObjectCreationException`. The common fix is to swap in `OmitOnRecursionBehavior`, which truncates the graph at the cycle. This is the single most-searched AutoFixture error.

Customization APIs layer on top: `fixture.Build<T>().With(x => x.Name, "foo").Without(x => x.Id).Create()` for one-off shaping, `fixture.Customize<T>(...)` for type-wide rules, and `ICustomization` classes (composed via `AutoDataAttribute` subclasses) for reusable, project-wide conventions. `fixture.Freeze<T>()` pins a single instance so every subsequent request for that type — including nested dependencies — receives the same object, which is how you inject a specific mock into a SUT.

## Production Notes

- **Random data breeds flaky tests.** Generated values are non-deterministic across runs. A test that passes on `148` but relies on an unstated invariant (e.g. "value is single-digit", "string parses as a date") will fail intermittently. Assert on relationships, not on specific generated values, and use `Freeze`/`Build().With(...)` to pin anything load-bearing.
- **Strings are GUIDs.** `Create<string>()` returns something like `"Name<guid>"`. Code that validates format (emails, phone numbers, length-limited columns) will reject them — customize those types explicitly or reach for a realistic-data generator like Bogus.
- **Recursion throws by default.** EF Core entities and other bidirectional graphs will hit `ThrowingRecursionBehavior`. Add `OmitOnRecursionBehavior` early or you'll rediscover it in every new test class.
- **Reflection cost.** Building large object graphs is reflection-heavy and not free. In tightly-looped or very large test suites AutoFixture can be a measurable fraction of run time; reuse a configured `Fixture` and avoid regenerating huge graphs per test.
- **Overuse hides intent.** `[AutoData]` on everything makes tests terse but can obscure which inputs actually matter. The idiomatic middle ground is `[InlineAutoData]` — pin the significant arguments inline, let AutoFixture fill the rest.
- **Version compatibility with mocking libs.** The bundled `AutoMoq`/`AutoNSubstitute` packages target a compatibility range and may lag the newest mocking-library features; the README advises installing the latest mocking package alongside AutoFixture rather than relying on the bundled version.
- **v5 has been in preview a long time.** The default branch is `release/5.0.0` and v5 ships only as `-preview` packages; stable releases remain on the 4.x line (4.18.0 at time of writing). Preview packages explicitly do not follow SemVer and may be unlisted — don't pin production test suites to them.

## When to Use / When Not

**Use when:**
- You write many unit tests in C#/.NET and spend visible effort on irrelevant Arrange boilerplate.
- You want tests that survive constructor/property changes without mechanical edits.
- You're doing classic TDD and value SUT factories plus auto-injected mocks (`Freeze` + AutoMoq).

**Avoid / reconsider when:**
- You need realistic, format-valid data (names, emails, addresses) — that's a Bogus/GenFu job, not AutoFixture's GUID-strings.
- You need deterministic, human-readable fixtures for golden-file or snapshot tests.
- Your team reads tests as documentation and wants every input visible at the call site.
- You're property-based testing — FsCheck/CsCheck model the input space directly rather than sampling one anonymous value.

## Alternatives

- bchavez/Bogus — realistic fake data (names, emails, locales) with fine-grained control; use instead when the *shape/validity* of data matters more than eliminating boilerplate.
- fscheck/FsCheck — property-based testing that generates many inputs to falsify properties; use instead when you want coverage of the input space, not one anonymous specimen.
- nickdodd79/AutoBogus — Bogus + automatic recursive population; use instead when you want AutoFixture-style auto-generation but with Bogus's realistic values.
- MisterJames/GenFu — convention-based realistic test data for .NET; use instead for lighter, readable seed data without the builder pipeline.
- devlooped/moq or nsubstitute/NSubstitute — mocking only; pair *with* AutoFixture (via AutoMoq/AutoNSubstitute) rather than replace it.
