# sqlite/sqlite

> The most widely deployed database engine in the world — a public-domain, serverless, single-file SQL engine that ships inside phones, browsers, planes, and applications rather than running as a server.

[GitHub repo](https://github.com/sqlite/sqlite) ·
[Official website](https://sqlite.org) ·
License: Public Domain

## Overview

SQLite is an embedded relational database written in C by D. Richard Hipp, first released 2000-05-29[^1]. Unlike PostgreSQL or MySQL, it is not a client/server system: there is no process to run, no port to open, no configuration. The entire database — tables, indexes, triggers, schema — lives in a single cross-platform file on disk, and the "server" is a library linked directly into the host application. This is why it is, by a wide margin, the most-deployed SQL engine that exists: it is embedded in Android, iOS, macOS, Windows 10+, every major browser, Python's standard library, and countless applications that never advertise it[^2].

This GitHub repository is an **official read-only mirror**, not the source of truth. SQLite is developed in [Fossil](https://fossil-scm.org/) — a version-control system Hipp wrote specifically to support SQLite — and the canonical check-in names differ from Git commit hashes[^3]. The project famously **does not accept pull requests**: because the code is dedicated to the public domain, accepting outside contributions could reintroduce copyright and compromise that status[^4]. As of 2026 the mirror carries roughly 10,000 stars and 1,500 forks, but those numbers understate the project entirely — SQLite's reach is measured in the trillions of live databases, not GitHub engagement.

The defining tension is scope discipline. SQLite deliberately refuses features that would make it a server (network access, per-row locking, multi-writer concurrency) in exchange for being small, embeddable, and extraordinarily reliable. Its test suite has 100% branch coverage via a separate proprietary harness (TH3), and the developers commit to supporting the on-disk file format and the library through the year 2050[^5]. You adopt SQLite for that stability and simplicity, not for write throughput under contention.

## Getting Started

Most languages ship SQLite bindings; you rarely install the engine directly. The CLI and the C library:

```bash
# macOS / Linux — CLI shell
brew install sqlite       # or: apt install sqlite3

# Open (or create) a database file
sqlite3 app.db
```

```sql
-- Inside the sqlite3 shell
PRAGMA foreign_keys = ON;   -- OFF by default; must be enabled per-connection
PRAGMA journal_mode = WAL;  -- concurrent readers + one writer

CREATE TABLE post (
  id     INTEGER PRIMARY KEY,      -- alias for rowid; autoincrementing
  title  TEXT NOT NULL,
  author TEXT
) STRICT;                          -- STRICT enforces declared column types

INSERT INTO post (title, author) VALUES ('hello', 'drh');
SELECT * FROM post WHERE author = 'drh';
```

To embed in C, the recommended path is the **amalgamation**: the entire engine concatenated into one `sqlite3.c` file (200K+ lines) plus `sqlite3.h`. Compiling from the amalgamation runs about 5% faster than compiling the individual source files, because the compiler can inline across the whole engine[^6].

## Architecture / How It Works

SQLite is a stack of well-separated modules, each with a public header and a private `*Int.h`:

- **Tokenizer + Parser** — SQL text is tokenized and fed to a LALR(1) parser generated by **Lemon** (`parse.y` → `parse.c`), a parser generator Hipp also wrote and ships in `tool/`.
- **Code generator** — produces bytecode for a register-based virtual machine.
- **VDBE (Virtual Database Engine)** — `vdbe.c` executes prepared statements as bytecode programs. `EXPLAIN` disassembles them; this indirection is what lets one code path serve `sqlite3_step()` across every platform.
- **Query planner** — `where.c` analyzes `WHERE` clauses and chooses indexes. It uses a cost model informed by `ANALYZE` statistics; the Next-Generation Query Planner (NGQP, 3.8.0) replaced the older nearest-neighbor optimizer[^7].
- **B-Tree** — `btree.c` implements the on-disk storage as B-trees of fixed-size pages.
- **Pager** — `pager.c` handles transactions, atomic commit, and rollback, mediating between the B-tree and the OS.
- **VFS (Virtual File System)** — `os_unix.c` / `os_win.c` implement a pluggable OS-abstraction layer. Swapping the VFS is how SQLite runs in-memory, over custom storage, or in exotic environments.

The single-writer model flows from this design. In rollback-journal mode a writer takes an exclusive lock on the whole file. **WAL mode** (`journal_mode=WAL`, added in 3.7.0, 2010) changed this so that readers do not block a writer and a writer does not block readers — but there is still only **one writer at a time**[^8]. There is no row-level or table-level locking; concurrency is file-level.

Dynamic typing is another deliberate departure from SQL norms. Columns have **type affinity**, not strict types: an `INTEGER` column will happily store a string unless the table is declared `STRICT` (added 3.37.0, 2021). This flexibility is convenient and a frequent source of data-integrity surprises for developers expecting Postgres-like enforcement.

## Production Notes

- **Foreign keys are OFF by default.** `PRAGMA foreign_keys = ON` must be issued on every connection, every time. Constraints declared in DDL are silently ignored otherwise — one of the most common data-integrity footguns.
- **"database is locked" (SQLITE_BUSY)** is the classic operational error. It comes from the single-writer model plus a busy timeout that defaults to 0. Set `PRAGMA busy_timeout = 5000` and use WAL mode. SQLite is a poor fit for many concurrent writers regardless.
- **WAL has caveats.** It requires shared memory, so it does **not** work reliably on network filesystems (NFS, SMB). The `-wal` and `-shm` sidecar files must travel with the main database. A checkpoint is needed to fold the WAL back into the main file; unbounded WAL growth under sustained load is a known operational issue.
- **Default page cache and durability.** `PRAGMA synchronous = NORMAL` (safe with WAL) trades a small durability window for large write throughput gains vs `FULL`. Bulk loads should wrap inserts in an explicit transaction — autocommit does one fsync per statement.
- **No network access.** SQLite is in-process only. "Distributed SQLite" (rqlite, dqlite, LiteFS, Turso/libSQL) are external layers that add replication on top; the core engine has none.
- **Amalgamation vs system library.** Vendoring `sqlite3.c` pins an exact, well-tested version and enables compile-time `SQLITE_OMIT_*` / `SQLITE_ENABLE_*` flags (FTS5, JSON, R-Tree, etc. are opt-in). Relying on the OS-provided libsqlite3 means inheriting whatever version and build flags the distro chose — often an older one with features omitted.
- **Upgrades are famously painless.** The file format is backward- and forward-compatible and guaranteed stable to 2050; upgrading the library almost never breaks existing databases. This is the inverse of the usual database upgrade story.

## When to Use / When Not

**Use when:**
- You need an embedded, zero-administration store: desktop/mobile apps, CLI tools, on-device caches, config, edge functions.
- The workload is read-heavy or has a single writer.
- You want a self-contained, portable data file and long-term format stability.
- You want to test against real SQL without standing up a server (though behavior differs from Postgres/MySQL).

**Avoid when:**
- You need many concurrent writers or high write throughput under contention — use a client/server database.
- Multiple machines must access the same database over a network filesystem — the locking model is unsafe there.
- You need strict typing, rich types, or server-side features (stored procedures, materialized views, fine-grained access control) out of the box.
- The workload is large-scale analytical/OLAP scanning — a columnar engine will be far faster.

## Alternatives

- duckdb/duckdb — use instead when the workload is analytical/OLAP; DuckDB is columnar and vectorized where SQLite is row-oriented and transactional.
- postgres/postgres — use instead when you need a real multi-user server, strict types, and concurrent writers.
- tursodatabase/libsql — use instead when you want a SQLite-compatible engine with an open-contribution model and built-in replication.
- google/leveldb or facebook/rocksdb — use instead when you need an embedded key-value store rather than SQL.
- berkeleydb — use instead for embedded key-value with a long enterprise track record (Oracle-licensed).

|---------|------|-------|
