# libgdx/libgdx

> A code-first Java game-development framework that compiles the same source to desktop, Android, iOS, and the browser.

[GitHub repo](https://github.com/libgdx/libgdx) ·
[Official website](https://libgdx.com) ·
[License: Apache-2.0](https://github.com/libgdx/libgdx/blob/master/LICENSE)

## Overview

libGDX is a game *framework*, not a game *engine* — there is no editor, no scene inspector, and no visual workflow. You write Java (or Kotlin/Scala on the JVM), and libGDX gives you a thin, uniform abstraction over graphics, audio, input, file I/O, and networking that behaves the same across every target[^1]. Started by Mario Zechner ("badlogic") around 2009–2010, it reached 1.0 in April 2014 and has been continuously maintained since[^2]. As of 2026 it remains actively developed, with commits landing weekly and roughly 25k stars.

The defining design choice is the **backend model**: one core module written against interfaces, plus a per-platform backend that implements them. LWJGL3 drives desktop, an Android backend wraps the Android SDK, an iOS backend cross-compiles JVM bytecode to native ARM, and a GWT backend transpiles your Java to JavaScript for the browser. Your game code touches only the interfaces (`Gdx.graphics`, `Gdx.input`, `Gdx.files`), so a single codebase runs everywhere — with the browser target imposing the sharpest constraints.

The tradeoff is deliberate: libGDX gives you low-level control and no imposed structure, at the cost of building everything above `SpriteBatch` and `Texture` yourself (or from the large third-party ecosystem). Teams that want a drag-and-drop editor are in the wrong place; teams that want to own their architecture and ship the same binary logic to five platforms are in the right one.

## Getting Started

libGDX is not downloaded directly — you generate a Gradle project with the setup tool. The original `gdx-setup` is effectively superseded by the community-maintained **gdx-liftoff** generator[^3].

```bash
# Download gdx-liftoff.jar from its releases page, then:
java -jar gdx-liftoff.jar
# Pick platforms (LWJGL3, Android, iOS, HTML5), extensions (Box2D, Freetype), and generate.
cd my-game && ./gradlew lwjgl3:run
```

A minimal `ApplicationListener` that clears the screen and draws a texture:

```java
public class MyGame extends ApplicationAdapter {
    private SpriteBatch batch;
    private Texture texture;

    @Override public void create() {
        batch = new SpriteBatch();
        texture = new Texture("badlogic.jpg");   // loaded from the assets/ folder
    }

    @Override public void render() {
        ScreenUtils.clear(0f, 0f, 0f, 1f);
        batch.begin();
        batch.draw(texture, 100, 100);
        batch.end();
    }

    @Override public void dispose() {   // native resources are NOT freed by the GC
        batch.dispose();
        texture.dispose();
    }
}
```

## Architecture / How It Works

Everything hangs off the static `Gdx` holder. On startup a backend sets `Gdx.app`, `Gdx.graphics`, `Gdx.audio`, `Gdx.input`, `Gdx.files`, and `Gdx.gl`, then drives your `ApplicationListener`'s `create → resize → render (loop) → pause/resume → dispose` lifecycle. Because these are global statics bound at launch, your game logic never imports platform-specific classes.

Rendering sits directly on **OpenGL ES 2.0/3.0** (desktop uses a GL-ES-compatible profile). The workhorses are `SpriteBatch` (batches many textured quads into few draw calls, flushing on texture change or `end()`), `Texture`/`TextureAtlas`, `OrthographicCamera`/`Viewport` for 2D, and `ShaderProgram` for custom GLSL. A separate 3D API (`ModelBatch`, `Environment`, glTF via third-party loaders) shares the same GL layer.

Native-heavy modules are C/C++ libraries reached through **JNI**, with the glue generated by **gdx-jnigen** and cross-compiled per platform: **Box2D** (2D physics), **Bullet** (3D physics), and **gdx-freetype** (runtime TrueType rasterization). These expose Java handles that wrap native pointers — a detail that becomes a footgun (see below).

The four backends do not offer identical capabilities:

- **LWJGL3** — the default desktop backend; multi-window, better HiDPI, replaced the older LWJGL2 backend.
- **Android** — thin wrapper over `Activity`/`GLSurfaceView`; subject to GL context loss on pause/resume.
- **iOS** — bytecode is ahead-of-time compiled to native ARM. Historically via RoboVM; after RoboVM's original maintainer discontinued it in 2016, libGDX moved to the community **MobiVM** fork[^4].
- **GWT / HTML5** — Java is transpiled to JavaScript at build time. This is the constrained target: no threads, no arbitrary reflection, `long` is emulated (slow), and only the JRE-emulated subset of the standard library is available.

`scene2d` and `scene2d.ui` provide an optional retained-mode scene graph and skinnable widget toolkit built on top of the same primitives — the closest libGDX comes to "engine" territory.

## Production Notes

**Manual disposal is mandatory.** `Texture`, `SpriteBatch`, `Sound`, `BitmapFont`, `FrameBuffer`, `ShaderProgram` and every physics world implement `Disposable`. They hold GPU or native memory the JVM garbage collector cannot see or reclaim. Forgetting `dispose()` leaks steadily; the leak is invisible in JVM heap tooling because it lives outside the heap.

**GWT/HTML5 will surprise you late.** Code that runs fine on desktop can fail to compile or misbehave under GWT: reflection needs explicit `.gwt.xml` configuration, `java.util` support is partial, `long` arithmetic is slow, and there is no threading. Prefer libGDX's own collections (`Array`, `ObjectMap`, `IntArray`) over `java.util` ones — they avoid autoboxing and are GWT-safe. Test the web target early and often; discovering an incompatibility after months of desktop-only development is a classic libGDX regret.

**Android context loss.** When an Android app is paused, the GL context can be destroyed and recreated. libGDX reloads "managed" resources (`Texture`, some meshes) automatically, but anything you created manually — custom `FrameBuffer`s, non-managed meshes, shaders — must be recreated in `resume()` or it renders black.

**JNI object lifetime.** Box2D/Bullet handles wrap raw native pointers. Holding a `Body` or `Fixture` reference after its `World` is disposed, or after the body is destroyed, is use-after-free at the native layer — it can crash the JVM rather than throw. Null your references on destruction and never touch a physics object outside its world's step boundaries.

**SpriteBatch performance.** Each texture switch forces a flush (a draw call). Pack sprites into a `TextureAtlas` so unrelated sprites share one texture and batch together; unpacked textures silently cap you at a few hundred draw calls per frame. Watch `batch.renderCalls` while profiling.

**Version/upgrade cadence.** Releases are infrequent and generally low-drama; the long 1.9.x series (2016–2020) and later 1.10–1.13 line rarely break source compatibility. The larger migration pains have been ecosystem-side: the LWJGL2→LWJGL3 backend switch, and the iOS RoboVM→MobiVM transition, both of which changed project setup more than game code.

## When to Use / When Not

**Use when:**
- You want one Java/Kotlin codebase shipping to desktop, Android, iOS, and web with near-identical logic.
- You prefer writing your own architecture over adopting an engine's conventions.
- You're building 2D games (its sweet spot) or moderate 3D, and want direct GL access when needed.
- You value a permissive Apache-2.0 license with no runtime royalties.

**Avoid when:**
- You want a visual editor, scene tooling, or a rapid drag-and-drop workflow — use Godot or Unity.
- Your team is small and would rather assemble a game from prefabs than build systems from primitives.
- Your primary target is the browser and you need heavy multithreading or unrestricted reflection.
- You're doing serious 3D with PBR pipelines and tooling out of the box — libGDX's 3D is capable but bring-your-own.

## Alternatives

- godotengine/godot — full open-source engine with an editor and scene system; choose it when you want tooling instead of a bare framework.
- jMonkeyEngine/jmonkeyengine — Java, 3D-first with a scene graph and SDK; better when 3D and built-in editors matter.
- MonoGame/MonoGame — same code-first, no-editor philosophy in C#/.NET (XNA lineage); use it if you prefer the .NET ecosystem.
- korlibs/korge — Kotlin-first multiplatform 2D engine; use it when you want a more batteries-included Kotlin workflow.
- LWJGL/lwjgl3 — the raw GL/OpenAL/GLFW bindings libGDX sits on; drop to it only when you want zero abstraction.
